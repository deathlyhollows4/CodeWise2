## Reproducible setup and historical installation stages

The tested dedicated installation used `infra/runner/bootstrap-wsl.ps1`, with the exact owned distro `CodeWise2Runner` and Ubuntu24.04. That reviewed entrypoint transfers the Linux files, installs the pinned tools, protects private credentials and verifies the fixed canaries. Its `-Resume` mode requires recorded ownership of a distro created by this bootstrap. Use installation actions only within their explicitly authorized scope; routine app startup uses the existing private configuration.

1. In ordinary PowerShell run `pwsh -File infra/runner/install-wsl.ps1` for inspection. A bootstrap-only host may lack named-distro installation; this machine now has verified WSL 3.0.1 with named-distro support.
2. After explicit approval, open an Administrator PowerShell through Windows UAC and run `pwsh -File infra/runner/install-wsl.ps1 -Install`. If named-distro support is absent, this installs WSL **platform only** using `wsl --install --no-distribution`. It never reboots automatically. Restart manually if Windows requests it, then `wsl --update`.
3. Inspect current `wsl --help` and existing distros. Create a **dedicated CodeWise2Runner** distro, never reuse an everyday Ubuntu environment. If the updated installed client advertises `--name`, script rerun uses `wsl --install --distribution Ubuntu --name CodeWise2Runner --no-launch` and exits unchanged if that name already exists. Otherwise use Microsoft's documented `wsl --import CodeWise2Runner <new-install-directory> <verified-official-Ubuntu-ARM64-rootfs.tar> --version 2` after obtaining/verifying an official rootfs. This fallback download/import is a separate reviewed action; no arbitrary rootfs is bundled.
4. Copy supplied `infra/runner/wsl.conf` into that distro's `/etc/wsl.conf` as root. Disable drive automount, Windows process interoperability and Windows PATH injection. Enable systemd. Terminate **only** `CodeWise2Runner` and restart it to apply the config. Never terminate other distros.
5. Copy `setup-linux.sh`, `broker.py`, `verify-canaries.py` and both supplied systemd units through a reviewed temporary transfer, then remove any temporary host drive mount before executing code. Run `sudo bash setup-linux.sh` inside the dedicated distro. Install the units at `/etc/systemd/system/`, then `sudo systemctl daemon-reload` and `sudo systemctl enable --now var-local-lib-isolate.mount codewise2-runner.service`. Disabling swap in the dedicated environment and checking cgroup/mount/kernel controls remain setup gates; do not change global Windows/other-distro settings without approval.
7. Run `sudo python3 /opt/codewise2-runner/verify-canaries.py`. It runs actual compiled Java/C++ and Python fixtures plus network/files/environment, compilation boundary, CPU/wall/memory/output/process and read-only runtime canaries. ## Boundary and remaining work

Privileged controller interprets only a fixed language, source, stdin and bounded limits. It invokes isolate via an argument array, never shell text. Compilation and execution both run as isolate's unique unprivileged UID in new network/mount/process namespaces. Runtime mounts are a minimal read-only allowlist, with explicit `/box` and public JDK config; `/dev` contains only null/zero/random/urandom nodes. Program environment does not inherit controller tokens. One sandbox at a time; backend owns durable bounded queue/idempotency. Authenticated cancellation signals only the owned isolate keeper and acknowledges workspace cleanup; the real cancellation canary passes.

The controller is root inside a dedicated distro because isolate requires privileged namespace/cgroup control. It is not a general execution endpoint for browser clients. Authentication token protects controller. App canary attestation has a 24h expiry and matches runtime identity including the Linux boot ID, binary/control digests and core policy. Attestation alone does not prove every attack impossible. Independent source review and actual canaries have found and repaired privacy and resource guards; the core-policy gate is now verified in the active tracked boot with25 actual checks passing. Scalar, array, native node and stateful references have actual three-language passes. Final exact whole-bank runtime coverage and independent publication reviews remain separate gates. WSL is a virtualized Linux prerequisite, not itself the learner sandbox.

The stock kernel value `|/wsl-capture-crash %t %E %p %s` sends crashes to a collector outside the sandbox. Per-process core limit0 alone is not sufficient evidence for this pipe. The reviewed optional `core-policy.py` proposes exact non-pipe value `core`, backs up the exact previous value durably, quiesces only the named controller, cleans box0 and verifies empty sandbox child cgroups, and refuses concurrent/unknown changes. Restore uses the exact owned backup and leaves the controller stopped. This affects the **shared WSL2 VM kernel**, including other distros in that VM; the user authorized this reversible scope, and apply has run with the prior value preserved. Actual restore remains untested; trusted temporary-file restore guards have eight passing tests. WSL/Windows restart and .wslconfig changes are not part of this proposal.

If the VM resets the pattern on restart, readiness fails closed. Explicit approved-policy reapplication and fresh canaries would be needed. Production startup owns a hidden tracked named-distro client for the app lifetime and stops only that verified client during app shutdown. The earlier eight-hour development anchor in runner-lifetime.json is historical setup evidence. Systemd services alone do not keep WSL alive. The lifecycle never automatically reapplies the VM-wide crash policy.
