# CodeWise2 architecture

The loopback Node server serves the bundled React/Vite interface and same-origin APIs. Public runtime schemas in packages/contracts validate incoming requests, public problem DTOs and judge result accounting. The frontend never receives stored credentials, private suites or reference code. The compiled backend resolves the trusted judge/content loader from the repository root; startup import failures are explicit.

SQLite is the durable authority for draft revisions, immutable submission snapshots, queue records, assistance/evidence, recommendations, learner settings, generation messages/chunks, bookmarks and notes. Foreign keys, WAL, busy timeout and explicit transactions serialize writes. A job request's idempotency key deduplicates retries; at most two execution jobs run concurrently. Restart marks unfinished execution/tutoring interrupted and never automatically retries inference.

Three authorities remain separate: the isolated execution adapter determines acceptance; the versioned deterministic learning engine derives recommendations/evidence; DeepSeek explains requested context. Unavailable isolation preserves reading/editing and reports infrastructure failure. No submitted source is executed by a host shell.

DeepSeek requests use a fixed official HTTPS destination. Keys are protected with current-user Windows DPAPI or authenticated encryption on other systems, never returned to the browser. Only visible content deltas are retained. Each content/event transaction commits before SSE broadcast; replay loads persisted sequence IDs. Lesson reopening performs no inference. Original responses remain separate from annotations/new versions.

Content packs separate public statement/examples/starters from private tests/checkers/references. Packs stay draft until independent review, runtime evidence, rights/progression checks and immutable hashes satisfy publication. Curriculum counts reflect only genuinely published packs. Review/proficiency states describe evidence rather than fabricated probability scores.

Known release gaps and actual evidence are recorded in release-evidence/backend-status.md and coordinator BUILD_STATUS.md. These descriptions do not imply unavailable runner/full-bank/live-provider gates have passed.

Review scheduling uses explicitly imported `@js-temporal/polyfill`0.5.1 (ISC) with `jsbi`4.3.2 (Apache-2.0), using the runtime's IANA timezone data. No global `Temporal`, `Date` or system timezone setting is modified. Calendar-day addition follows the [Temporal ZonedDateTime contract](https://tc39.es/proposal-temporal/docs/zoneddatetime.html); user timezone changes intentionally recompute due instants from immutable UTC evidence. The shared delivery-scope JSON defines243 questions with3 languages and3 visible cases each;191 preserved IDs require at least200 hidden cases and52 explicit remaining IDs require exactly60. The core bank is published; additional ancillary/application release evidence remains separately tracked.

Each profile admits one application owner before catalogue loading, startup recovery or port binding. `profile-owner-lock.sqlite` is a separate rollback-journal database whose open `BEGIN EXCLUSIVE` transaction holds SQLite's OS-backed lock for the app lifetime; the learning database remains WAL. A second instance fails closed without changing active jobs. The atomic `profile-owner.json` marker is diagnostic only: PID/time/expiry never grant ownership. Normal shutdown releases the lease, and a crashed process loses its kernel lock so one successor can safely recover. See SQLite's [transaction](https://sqlite.org/lang_transaction.html) and [VFS locking](https://www.sqlite.org/lockingv3.html) contracts.

Sources separates immutable author provenance from current independent review status. The server binds category records to the cached pack's status-neutral content identity, bounds each record read to64KiB, and reports missing/stale/invalid categories as pending. It does not rewrite provenance or expose private reviewer text/reference code. Source identity fields come from the validated pack rather than a provenance override.

Learning classifications are separately versioned presentation data under `content/learning-tags.json` with an independently reviewed `content/learning-tags-review.json`. Their schema/approval/catalogue/current-core-identity gate is additional to oracle, category and language gates. Secondary topics do not inflate primary quotas or grant skill evidence. This separation preserves immutable grading/public snapshots and historical lessons while providing a current-only metadata endpoint with explicit version checks. Runtime wiring/approval and the integrated release audit are recorded separately from the earlier243 publication transaction; final application acceptance is not inferred from either alone.
